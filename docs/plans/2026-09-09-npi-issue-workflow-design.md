# NPI 异常履历闭环流程 — 设计（2026-09-09）

> 需求方：王老师。经 `/brainstorm` 逐节确认后定稿，确认后开发。
> 涉及页面：`/eam/npi/npiProject` → 项目详情 → 异常履历页签。
> 关联既有设计：`docs/plans/2026-09-04-npi-project-management-design.md`。

## 1. 背景

原异常履历只有 `open / closed` 两态、一个「结案」按钮，看不出"谁在处理、处理到哪一步、是简单处理还是需要长期优化"。
本次把它改造成**可闭环的状态机**：新建 → 处理人处理 / 优化 → 阶段责任人结案，并支持责任人打回返工。

## 2. 状态机

### 2.1 四个状态

| 值 | 显示 | 含义 |
|---|---|---|
| `pending` | 待处理 | 新建后的初始态 |
| `handled` | 已处理待确认 | 处理人填了临时措施 |
| `optimized` | 已优化待确认 | 处理人填了临时措施 + 长期措施 |
| `closed` | 已结案 | 阶段责任人确认，终态 |

### 2.2 流转边

```
新建 ──────────────────────────→ ① 待处理
① ──[处理人·处理]  临时措施必填 ──→ ② 已处理待确认
① ──[处理人·优化]  临时+长期必填 ─→ ③ 已优化待确认
② ──[处理人·优化]  补长期措施 ────→ ③ 已优化待确认
② ──[责任人·结案] ───────────────→ ④ 已结案
③ ──[责任人·结案] ───────────────→ ④ 已结案
② ──[责任人·打回]  理由必填 ──────→ ① 待处理
③ ──[责任人·打回]  理由必填 ──────→ ① 待处理
④ 终态，不再流转
```

打回回到 ① 后，处理 / 优化两条路重新开放，**已填措施内容保留不清空**（处理人在原基础上改），打回理由进流转记录。

### 2.3 按钮矩阵

| 状态 | 处理 | 优化 | 结案 | 打回 | 编辑 |
|---|:--:|:--:|:--:|:--:|:--:|
| ① 待处理 | ✔ | ✔ | | | ✔ |
| ② 已处理待确认 | | ✔ | ✔ | ✔ | ✔ |
| ③ 已优化待确认 | | | ✔ | ✔ | ✔ |
| ④ 已结案 | | | | | |

### 2.4 权限口径（demo 取舍）

demo 登录的是超级管理员，**不做硬校验**：结案 / 打回按钮常亮，点击时二次确认写明「以阶段责任人 **XXX** 的身份确认…」，操作人记入流转记录。
真实上线接权限时，只需把这层身份判断换成当前登录用户，改一处。

## 3. 界面

### 3.1 三个新弹窗 + 一个确认框

| 入口 | 弹窗内容 | 结果 |
|---|---|---|
| 处理 | 顶部只读带出「阶段/类型/问题/原因」+ **临时措施**（必填） | → ② |
| 优化 | 同上只读区 + **临时措施**（必填，从 ② 进入时预填原值可改）+ **长期措施**（必填） | → ③ |
| 打回 | 只读展示处理人已填措施 + **打回理由**（必填） | → ① |
| 结案 | 确认框「以阶段责任人 XXX 的身份确认本条异常结案？」 | → ④，写入实际完成日期 |

### 3.2 表格改动

1. **状态列**四态标签：待处理（灰）· 已处理待确认（橙）· 已优化待确认（蓝）· 已结案（绿）。
2. **操作列**按 2.3 矩阵动态显示，固定右侧；已结案行只剩「查看」。
3. **新增展开行**：时间线展示该条异常完整流转记录（时间 · 操作人 · 动作 · 备注）。这是"一眼看出流程"的落点。
4. **状态计数筛选条**：新增异常按钮同一行右侧显示四态计数，点击按状态筛选。

### 3.3 新建弹窗

去掉「临时措施 / 长期措施」两个框（措施归到它们真正产生的环节）。字段为：
所属阶段 → 异常类型 → 问题 → 原因 → 阶段责任人（随阶段自动带出，只读）→ 处理人（下拉，可输入新人员）→ 发生日期 → 计划完成。

## 4. 数据模型与唯一入口

### 4.1 类型（`src/mock-data/eam-npi.ts`）

```ts
export type IssueStatus = 'pending' | 'handled' | 'optimized' | 'closed'
export type IssueFlowAction = 'create' | 'handle' | 'optimize' | 'reject' | 'close'

export interface NpiIssueFlow { time: string; action: IssueFlowAction; operator: string; remark: string }

export interface NpiIssue {
  …
  status: IssueStatus
  flow: NpiIssueFlow[]   // 新增：流转记录
}
```

### 4.2 唯一入口（系统性解决，禁止单点修复）

store 只开一个 `transitionIssue(id, action, payload)`，集中做「合法性校验 → 写措施字段 → 追加流转记录 → 持久化」。
处理 / 优化 / 打回 / 结案四个按钮全部走它，不各写各的 `updateIssue`。

合法转移表与按钮矩阵是**同一份数据**：

```ts
export const ISSUE_ALLOWED_ACTIONS: Record<IssueStatus, IssueFlowAction[]> = {
  pending:   ['handle', 'optimize'],
  handled:   ['optimize', 'reject', 'close'],
  optimized: ['reject', 'close'],
  closed:    []
}
```

- 操作列按钮由这张表驱动渲染，不手写 `v-if="row.status === 'xx'"`；以后加状态，按钮自动跟上，不会漏出口。
- 非法流转在 store 内直接抛错，UI 提示。

### 4.3 旧数据兼容

localStorage 既有记录是 `open / closed` 两态、无 `flow` / `handler`。**不升 STORAGE_KEY**（避免丢掉页面上手建的项目），load 时统一 normalize：

- `open` → `pending`，`closed` → `closed`
- 缺 `flow` → 补一条 `create` 记录
- 缺 `handler` → 空串
